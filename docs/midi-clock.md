# Adding MIDI clock over USB

Goal: the Trio+ should be the MIDI clock master for other gear, over its
existing USB port.

Nothing here is implemented yet. This document is the design space, with the
hard constraints that the hardware enforces.

## The two hard constraints

**1. There is no USB-MIDI function to reuse.**
The unit enumerates as one vendor-HID interface (class 3, interrupt EP1 IN /
EP2 OUT). MIDI-over-USB is a *composite* device: class 1, subclass 3,
MIDIStreaming interface, bulk endpoints, class-specific descriptors and
requests. None of that exists in the current descriptor set, so "USB MIDI"
means writing a USB function, not toggling a flag.

**2. The MCU probably does not know the tempo.**
The looper/band/tempo logic lives on the DSP, on the other side of the SPI link
(`0x40008000`). That DSP is an **ADSP-21489 SHARC** (see
[hardware.md](hardware.md)), and its image ships as a VisualDSP++-style ASCII
`0xNN` loader stream. The MCU image contains no BPM/tempo strings or tables,
does not touch its on-chip ADC, and uses SysTick plus SPI0 for timing and
control. Until a bus capture (or DSP analysis) proves otherwise, assume the
tempo number reaches the MCU over SPI, if at all.

Reading a song from the SD card does not help either: `.tlsd` stores part
lengths in samples, not a BPM field, so it records the musical result rather
than a live tempo. See [sdcard.md](sdcard.md).

The owner's manual describes the tempo model the clock must match:

* **TEMPO is global and continuous**, with a centre detent at the learned
  tempo (1×), 2× at full clockwise and 0.5× at full counter-clockwise.
* Moving the knob enables **AUDIOLASTIC** time-stretching; the LED indicates
  that the playback tempo differs from the learned tempo.
* **ALT TIME** picks a half- or double-time interpretation of a part when the
  learned material supports it.
* Each part has its own learned tempo; adjacent parts can be tempo-matched
  when they are close, otherwise they play at their own rate.

For a clock generator this means the useful range is bounded to 0.5×–2× of a
per-part learned tempo, and the current value is a playback parameter rather
than a stored song field.

Constraint 2 is the real problem: a clock generator needs 24 pulses per quarter
note at the current tempo, and something has to own that number.

## Option A — USB-MIDI composite in the MCU firmware

Add a second interface (or replace HID) with:

* MIDIStreaming interface + class-specific endpoints,
* one bulk IN endpoint and one bulk OUT (for start/stop/continue and clock if
  the host sends it),
* a 1 ms (or faster) timer generating 24 PPQN clock bytes,
* class requests (`SET_LINE_CODING` analogue: `SET_CABLE`, jack descriptors),
* updated configuration/device descriptors, and the endpoint allocation in the
  UDP driver.

Cost: highest. Touches USB enumeration, which is the one thing that must keep
working or the unit will not be updatable or usable. Also requires solving
constraint 2.

Upside: a single cable, no host software, class-compliant on macOS/Windows/iOS.

## Option B — HID tempo report + host bridge

Keep the existing descriptors. Extend the vendor HID input report with a small
tempo/transport block (e.g. `report[0] = 0x7E`, BPM, bar/beat, running flag) and
let a small host daemon turn that into a virtual MIDI port emitting 24 PPQN
clock.

Cost: lowest on the firmware side — a descriptor-compatible report is a pure
payload addition, and the updater keeps working because VID/PID are unchanged.
Risk is contained to the app-side report parser, which already ignores unknown
report content.

Upside: no USB stack surgery, easy to iterate, easy to debug (the host can log
tempo), works on macOS and Windows with existing virtual-MIDI APIs (CoreMIDI
`MIDIClientCreateWithBlock`, Windows `winmm`/`teVirtualMIDI`).

Downside: needs a daemon running, and still requires the MCU to obtain tempo
from the DSP.

Jitter: USB HID interrupt transfers at 1–5 ms intervals are fine for *tempo
information*, but clock pulses should be generated by the daemon's own timer
from a stable BPM estimate, with phase correction — not by forwarding raw beat
events.

## Option C — hardware tap

Tap the SPI link (or a GPIO heartbeat) with a small MCU and emit DIN MIDI /
USB-MIDI from that. No firmware changes, no bricking risk.

Concrete tap points on the Trio+ (there is no SPI connector): the W25Q128FVSG
flash at **U3** pins 6 (CLK), 5 (MOSI), 2 (MISO), 4 (GND), or the **TP2/TP3/TP4**
test points if continuity shows they are the same nets. See
[hardware.md](hardware.md#spi-tap-points-rp2040-bridge). A Raspberry Pi Pico /
RP2040 can sniff the bus with PIO and enumerate as a USB-MIDI device at the same
time.

Cost: hardware. Requires opening the unit, finding a usable 3.3 V rail and the
SPI/transport signal, and reverse-engineering the tempo encoding on the wire.

Upside: reversible, independent of firmware updates, and it can also *receive*
clock if you want the Trio+ to follow external gear.

## Decision matrix

| | A: USB-MIDI in MCU | B: HID + host bridge | C: hardware tap |
|---|---|---|---|
| Brick risk | high | low | none |
| Needs DSP tempo decode | yes | yes | yes |
| Needs host software | no | yes | no |
| Updater still works | likely | yes | yes |
| Effort | weeks | days | days + soldering |
| Clock jitter | best | good with phase lock | good |

## Recommended path

1. **Dump the external flash.** A CH341A plus a SOIC-8 clip reads the 16 MB
   W25Q128FVSG. It shows how the DSP image, styles and ensemble audio are
   stored, how much space is free, and whether the MCU stages the update image
   there. Use `tools/dump_flash.sh` and `tools/analyze_flash.py`.
2. **Capture first.** With a Trio+ connected, record the USB descriptor set and
   the HID traffic during normal operation (`ioreg -p IOUSB -l`, `usbhid-dump`,
   or Wireshark with USBPcap). Confirm there is really no MIDI/audio alt setting
   at runtime.
3. **Find the tempo path.** Turn the tempo control and tap tempo while capturing
   SPI (logic analyser on the DSP link) and the HID reports. Also buzz out J8:
   if it is the SAM4S JTAG/SWD header, a J-Link gives you live RAM inspection and
   a recovery path.
4. **Prototype Option B.** It gives a working clock with a fraction of the risk,
   and the tempo plumbing it forces you to build is exactly what Option A needs
   later.
5. **Only then consider A**, on a sacrificial unit, with the stock image and a
   recovery procedure verified first.

## Safety notes for any firmware work

* Keep the VID/PID pair intact, or the updater will no longer enumerate the unit.
* Keep the image within the length the bootloader accepts (unknown; test with a
  no-op rebuild first).
* Re-flash the stock image and verify recovery **before** testing a patch that
  touches USB or the vector table.
* The update path is unsigned (XOR checksums only), so nothing will stop you
  from flashing a broken image.
